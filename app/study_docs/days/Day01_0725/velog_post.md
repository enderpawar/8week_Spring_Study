# [백엔드 기본기 Day 1] Spring MVC와 HTTP 상태 코드 — 요청은 어떻게 200·404 응답이 되는가

빈 Spring Boot 스켈레톤에서 `HelloController` 하나를 만들고, HTTP 요청이 컨트롤러를 거쳐 응답으로 바뀌는 흐름을 확인했다. 이 글은 `GET /hello`, `/health`, `/bye`와 미등록 경로 `/nope`에서 관찰한 상태 코드까지 다룬다. DTO 매핑과 입력 검증은 아직 적용하지 않았으므로 범위에서 제외한다.

## 한눈에 보기

- **문제:** `hello()`가 문자열만 반환하는데도 왜 `200 OK`가 되는지 설명하지 못했고, 처음에는 상태 코드를 DTO와 연결해 생각했다.
- **적용:** `@RestController`와 `@GetMapping`으로 요청을 메서드에 연결하고, 기본 응답과 `ResponseEntity`로 상태를 명시한 응답을 비교했다.
- **검증:** 실행 중인 애플리케이션에 HTTP 요청을 보내 `/hello` 200, `/nope` 404, `/health` 200, 수정 후 `/bye` 201을 확인했다.
- **한계:** 엔드포인트 자동화 테스트가 없고, `GET /bye`의 `201 Created`는 상태 코드 지정 방법을 확인하는 연습일 뿐 HTTP 의미에 맞는 API 설계는 아니다.

## 1. 문제를 이해하기 위한 이론

### 왜 HTTP 응답 계약을 알아야 하는가

컨트롤러가 반환하는 값은 단순한 Java 값으로 끝나지 않는다. 서버는 클라이언트에게 상태 코드, 헤더, 본문으로 구성된 HTTP 응답을 보낸다. 클라이언트는 본문뿐 아니라 상태 코드를 보고 요청의 성공 여부와 다음 행동을 판단하므로, 어떤 코드가 선택되는지 설명할 수 있어야 한다.

Day 1의 첫 코드는 문자열만 반환했다.

```java
@GetMapping("/hello")
public String hello() {
    return "Hello,StudyRoom!";
}
```

`@RestController`가 붙은 클래스에서 이 `String`은 뷰 이름이 아니라 응답 본문으로 처리된다. 메서드가 정상적으로 반환되고 별도의 응답 상태를 지정하지 않았으므로 응답 상태는 기본값인 `200 OK`가 되었다.

### 핵심 용어

- **HTTP 상태 코드:** 요청 처리 결과를 세 자리 숫자로 나타내는 응답 메타데이터다. 1xx는 정보, 2xx는 성공, 3xx는 리다이렉션, 4xx는 클라이언트 오류, 5xx는 서버 오류 계열이다.
- **응답 본문(body):** 클라이언트에게 전달하는 실제 데이터다. 상태 코드와 본문은 같은 응답에 포함되지만 서로 다른 역할을 한다.
- **`@RestController`:** Spring MVC가 요청 처리 대상으로 찾는 컨트롤러이면서, 메서드의 반환값을 HTTP 응답 본문으로 쓰도록 하는 애노테이션이다.
- **`@GetMapping`:** HTTP GET 요청의 경로를 컨트롤러 메서드에 매핑한다.
- **`ResponseEntity<T>`:** 응답 본문과 상태 코드 등을 함께 표현하는 Spring 타입이다. Day 1에서는 `ResponseEntity<String>`으로 상태와 문자열 본문을 직접 정했다.

DTO는 계층 사이에서 전달할 데이터의 형태를 정의한다. 반면 상태 코드는 HTTP 처리 결과를 나타낸다. 따라서 “DTO에 저장되어 있어서 200이 된다”는 설명은 데이터 구조와 프로토콜 메타데이터를 혼동한 것이다.

### 요청에서 응답까지의 흐름

```text
클라이언트의 GET 요청
→ DispatcherServlet이 요청을 받음
→ 요청 경로와 HTTP 메서드에 맞는 핸들러를 찾음
→ HelloController의 메서드를 호출함
→ 반환값을 HTTP 응답 본문으로 변환하고 상태 코드를 정함
→ 클라이언트가 상태 코드와 본문을 받음
```

`GET /hello`에는 `@GetMapping("/hello")`가 있으므로 `hello()`가 호출되고 문자열 본문과 `200 OK`가 반환된다. 반면 `/nope`에 대응하는 핸들러는 없었다. Spring MVC가 요청을 연결할 메서드를 찾지 못했고, Spring Boot의 오류 처리 흐름을 거쳐 `404 Not Found`가 반환되었다.

URL 경로와 Java 메서드 이름은 역할이 다르다. `@GetMapping("/hello")`의 `/hello`는 클라이언트가 사용하는 HTTP 계약이고, `hello()`는 Java 코드 내부의 식별자다. 둘을 같게 지을 수는 있지만 같아야 매핑되는 것은 아니다.

### CS 지식과 연결

이 흐름은 네트워크에서 배운 HTTP 요청·응답 구조가 프레임워크 코드와 연결되는 지점이다. 상태 코드는 응답의 상태줄에 속하고, `String` 값은 응답 본문이 된다. 또한 `@GetMapping` 목록은 “HTTP 메서드와 경로를 처리 함수에 연결한다”는 점에서 라우팅 테이블처럼 볼 수 있다. 등록된 항목이 없으면 매칭에 실패하고 404가 된다.

Java 컴파일 단계와 Spring의 요청 매핑 단계도 구분해야 한다. Java 컴파일러는 메서드 이름과 파라미터 타입으로 시그니처를 구분한다. 두 메서드에 서로 다른 `@GetMapping` 경로를 붙여도 이름과 파라미터 목록이 같다면 Java 단계에서 중복 선언 오류가 나므로 애플리케이션을 실행할 수 없다.

### 현재 코드에서 찾기

- [`HelloController.java`](https://github.com/enderpawar/8week_Spring_Study/blob/76a0fe5/app/src/main/java/com/example/studyroom/HelloController.java): Day 1에 만든 세 요청 매핑과 반환 상태를 확인할 수 있다.
- `HelloController.hello()`: 문자열 본문을 정상 반환해 기본 상태 `200 OK`가 되는 경로다.
- `HelloController.health()`: `ResponseEntity.status(HttpStatus.OK)`로 상태를 명시하지만 관찰되는 상태는 기본 응답과 같은 200이다.
- `HelloController.bye()`: `ResponseEntity.status(201)`로 기본값과 다른 상태를 지정한 독립 변형이다.

## 2. 설계 선택과 대안

### 기본 반환과 명시적 반환을 나란히 둔 이유

`/hello`는 `String`을 바로 반환하고, `/health`와 `/bye`는 `ResponseEntity<String>`을 반환하도록 구성했다. 이 비교로 “정상 반환이면 200이 되는 기본 동작”과 “코드에서 상태를 직접 선택하는 동작”을 분리해서 관찰할 수 있었다.

| 선택지 | 장점 | 단점·적합한 범위 |
|---|---|---|
| `String` 직접 반환 | 기본 성공 응답을 간단히 표현할 수 있다. | 상태나 헤더를 응답별로 세밀하게 정해야 할 때는 표현이 부족하다. |
| `ResponseEntity<String>` 반환 | 상태 코드와 본문을 한곳에서 명시해 의도를 드러낼 수 있다. | 항상 200인 단순 응답에서는 코드가 더 길어진다. |

`/health`에서 `HttpStatus.OK`를 쓴 것은 200이라는 의미를 이름으로 드러낸다. `/bye`의 실제 Day 1 코드에는 정수 `201`이 사용되었다. 동작은 하지만 `HttpStatus.CREATED`처럼 이름 있는 값을 사용하면 숫자의 의미를 코드에서 더 쉽게 읽을 수 있다.

다만 상태 코드를 명시할 수 있다는 것과 그 상태가 API 의미에 적절하다는 것은 별개의 판단이다. `201 Created`는 새 리소스가 생성되었음을 알리는 응답인데, `GET /bye`는 리소스를 생성하지 않는다. 이 엔드포인트는 상태 변경 방법을 비교하기 위한 학습 코드로만 해석해야 한다.

## 3. 코드로 적용하기

Day 1 커밋의 핵심 코드는 다음과 같다.

```java
@RestController
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "Hello,StudyRoom!";
    }

    @GetMapping("/health")
    public ResponseEntity<String> health() {
        return ResponseEntity
                .status(HttpStatus.OK)
                .body("OK");
    }

    @GetMapping("/bye")
    public ResponseEntity<String> bye() {
        return ResponseEntity
                .status(201)
                .body("Created");
    }
}
```

애플리케이션이 시작되면 Spring은 `@RestController`를 컨트롤러로 등록하고 각 `@GetMapping`의 경로를 메서드에 연결한다. 요청이 들어오면 일치하는 메서드가 실행된다. `hello()`는 본문만 반환하므로 기본 상태 200이 사용되고, `health()`와 `bye()`는 `ResponseEntity` 안에 적은 상태와 본문이 응답에 반영된다.

## 4. 예측 → 실행 → 차이 설명

| 구분 | 기록 |
|---|---|
| 실행 전 예측 | `/hello`는 “200일 것 같다(막연히)”, `/nope`는 404, `/health`는 여전히 200, `/bye`는 201이라고 예측했다. |
| 실행 | 애플리케이션을 실행한 뒤 `curl.exe -i`로 각 경로에 GET 요청을 보냈다. 코드 수정 뒤에는 실행 중인 애플리케이션을 재시작했다. |
| 실제 결과 | `/hello`는 `200 OK`, `/nope`는 `404 Not Found`, `/health`는 `200 OK`였다. `/bye`는 먼저 컴파일 오류가 발생했고, 네 가지 오류를 고친 뒤 `201 Created`를 확인했다. |
| 차이의 원인 | 상태 코드에 대한 예측은 맞았지만 `/hello`의 200을 DTO와 연결한 원리 설명은 틀렸다. 또한 다른 URL을 매핑하면 같은 Java 메서드 이름을 써도 된다고 볼 수 있었지만, 컴파일러는 Spring 애노테이션이 아니라 Java 메서드 시그니처로 중복을 판단했다. |

예측이 맞았다는 사실만으로 동작 원리를 안다고 할 수는 없었다. `/hello`의 200은 DTO 때문이 아니라 정상적으로 처리된 응답에 별도 상태가 지정되지 않았기 때문이다. `/health`는 결과 숫자는 같지만 `ResponseEntity`를 사용해 상태 선택을 코드에 드러냈다는 차이가 있다.

## 6. 막힌 지점과 오답 교정

### 상태 코드와 DTO를 같은 문제로 본 오답

처음에는 `hello()`에 상태 코드를 적지 않았는데 200이 나온 이유를 묻자 “HTTP 요청 반환 형식이 DTO로 미리 저장되어 있어서 그런가?”라고 생각했다. 원인은 HTTP 응답 메타데이터인 상태 코드와 데이터 전달 형태인 DTO의 역할을 분리하지 못한 것이었다.

교정한 설명은 다음과 같다. `@RestController` 메서드가 정상 반환하고 다른 상태를 지정하지 않으면 기본 상태 200이 사용되며, 반환한 문자열은 응답 본문이 된다. 같은 혼동을 막기 위해 이후에는 응답을 볼 때 상태 코드와 본문을 따로 확인한다. 이 문항은 정답을 본 직후 재설명한 것이어서 당시 복습큐에 +1일 재시험 대상으로 등록했다.

### URL 매핑과 Java 메서드 시그니처를 혼동한 오류

`/bye`를 작성하는 과정에서는 미완성 `HttpStatus.` 구문, `HttpStatus` import 누락, 세미콜론 누락, 기존 `health()`와 같은 메서드 이름·파라미터 사용으로 컴파일 오류가 발생했다. 이 중 중심 원리를 드러낸 오류는 메서드 중복이었다.

서로 다른 `@GetMapping` 경로는 Spring이 런타임에 요청을 분기할 때 사용한다. 그러나 같은 클래스 안의 메서드 선언이 유효한지는 그보다 먼저 Java 컴파일러가 검사한다. 메서드 이름을 `bye()`로 분리하고 나머지 문법 오류를 고친 뒤에야 실행과 HTTP 검증으로 넘어갈 수 있었다.

### 수정한 코드가 실행 중인 서버에 바로 반영된다고 본 문제

`.java` 파일을 수정했어도 이미 실행 중인 JVM이 자동으로 새 클래스를 사용하는 것은 아니었다. Day 1 환경에는 자동 재시작을 위한 별도 설정이 없었으므로 `bootRun`을 다시 실행한 뒤 응답을 확인했다. 이후에는 “소스 수정 → 다시 빌드·실행 → 요청 재검증” 순서를 지켜 오래된 실행 결과를 새 코드의 결과로 오인하지 않아야 한다.

## 7. 현재 한계와 다음 개선

- **자동화된 계약 검증 부재:** 현재의 `contextLoads()` 테스트는 Spring 애플리케이션 컨텍스트가 뜨는지만 확인한다. `/hello`, `/nope`, `/health`, `/bye`의 상태와 본문이 바뀌어도 잡아내지 못한다. 이후 웹 계층 테스트를 배울 때 정상·미등록 경로를 자동화된 테스트로 고정할 필요가 있다.
- **`GET /bye`와 201의 의미 불일치:** 상태 지정 동작은 확인했지만 GET 요청에서 리소스를 생성하지 않으므로 `201 Created`는 실제 API 계약으로 부적절하다. 생성 기능을 만들 때 POST 요청과 함께 다시 다뤄야 한다.
- **문자열 본문만 있는 예제:** 구조화된 요청·응답과 입력 검증은 확인하지 않았다. 로드맵의 다음 단계인 DTO와 도메인 분리에서 JSON 매핑을 학습해야 한다.
- **오류 응답 구조 미검증:** `/nope`의 404 상태만 확인했고 오류 본문의 형식은 분석하지 않았다. 전역 오류 처리 단계에서 응답 구조를 명시적으로 설계하고 검증해야 한다.

### Q2. `/nope`가 404이고 `/hello`가 200인 차이를 요청 처리 흐름으로 설명하면?

<details>
<summary>답 확인</summary>

`/hello`에는 GET 요청과 일치하는 `@GetMapping` 핸들러가 있어 `hello()`가 호출되고 정상 응답이 만들어진다. `/nope`에는 일치하는 핸들러가 없어 라우팅 단계에서 요청을 처리할 메서드를 찾지 못하고 404 응답으로 이어진다.

</details>

### Q3. URL 경로가 다르면 같은 이름의 무인자 Java 메서드를 두 개 선언해도 되는가?

<details>
<summary>답 확인</summary>

안 된다. URL 경로는 Spring의 요청 매핑 정보이고, Java 메서드 중복 여부는 이름과 파라미터 타입으로 구성되는 시그니처를 기준으로 컴파일 단계에서 판단한다. 애노테이션 값이 달라도 같은 시그니처의 메서드를 한 클래스에 중복 선언할 수 없다.

</details>

### Q4. `String` 직접 반환과 `ResponseEntity<String>` 반환은 언제 구분해서 사용할 수 있는가?

<details>
<summary>답 확인</summary>

항상 기본 성공 상태와 본문만 필요하면 `String` 직접 반환으로 단순하게 표현할 수 있다. 응답별 상태 코드나 헤더를 직접 정해야 한다면 `ResponseEntity<String>`으로 HTTP 응답을 명시할 수 있다. 다만 지정한 상태 코드가 해당 HTTP 메서드와 리소스 의미에 맞는지는 별도로 판단해야 한다.

</details>

## 정리하며

처음에는 200 응답을 DTO와 연결했지만, 실행 결과를 나눠 보면서 HTTP 상태 코드와 응답 본문은 서로 다른 역할이라는 점을 교정했다. 또한 Spring의 URL 매핑과 Java의 메서드 시그니처 검사는 서로 다른 단계에서 일어난다. `/bye`의 컴파일 오류는 요청이 컨트롤러에 도달하기 전에 Java 코드 자체가 유효해야 한다는 경계를 보여줬다.

이번 실습으로 기본 200, 미등록 경로의 404, `ResponseEntity`로 명시한 상태를 구분했다. 다음 단계에서는 DTO와 도메인을 분리하고, 문자열이 아닌 구조화된 요청과 응답이 어떻게 매핑되는지 확인한다.
