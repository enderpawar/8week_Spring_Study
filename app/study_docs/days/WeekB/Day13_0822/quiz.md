# Day13 (8/22, Week B D6) 누적시험 A+B 기록

범위: Week A(웹 계층) 전체 + Week B D1~D5(Flyway·JDBC·JPA·영속성 컨텍스트·변경 감지)

| # | 질문 | 학습자 답 | 판정 | 교정 |
|---|---|---|---|---|
| 1 | 요청 하나가 Controller→Service→Repository를 거치는 흐름과 각 계층 책임 | "Controller가 요청 분석→Service 호출, Service가 비즈니스 로직 수행→Repository 호출, Repository는 DB 인터페이스 역할, 역순으로 응답" | ✅ | Controller가 최종적으로 DTO+HTTP 상태코드를 반환한다는 점을 덧붙이면 더 완전함 |
| 2 | DTO(record)와 Domain을 왜 분리하나 | "dto는 데이터 모양 정의, domain은 immutable하지 않아서 상태 변경 로직 수행" | ⚠️ 절반 | 인과관계가 반대: "Domain은 상태 변경이 필요해서 immutable로 못 만든다"가 순서상 맞음. DTO는 "경계를 넘는 데이터 스냅샷"이라 상태가 필요 없어 record로 불변화한 것 |
| 3 | 생성자 주입을 쓰는 이유 3가지 이상 | (처음엔 "생성자 주입이 뭔지 기억 안 남" → 개념 재설명 후) "mock으로 교체 가능" → (힌트 후) "new로 직접 만들면 모든 호출부를 고쳐야 하지만 DI면 주입 대상만 바꾸면 됨(구현체 교체 시 Service 코드 무변경)" | ✅ | 두 가지 이유(테스트 시 mock 교체, 구현체 교체 시 Service 코드 안 건드림=DIP) 모두 힌트를 거쳐 도달 |
| 4 | 싱글톤 Bean과 무상태 설계가 왜 연결되는가 | "Bean 하나를 여러 요청이 동시에 공유하니까 인스턴스 필드에 값 넣으면 위험하므로 무상태로 설계해야 한다" | ✅ | 오늘 아침 인출(2번)과 동일 개념, 정확히 재현 |
| 5 | 순수 JDBC 대비 JPA가 실제로 추상화하는 것("커넥션 풀을 없앤다"가 오답인 이유 포함) | (힌트 후) "Hibernate가 매핑·SQL 생성을 대신 해준다" | ✅ | 커넥션 풀(HikariCP)은 JPA에서도 그대로 사용된다는 점까지 힌트로 짚어주고 학습자가 정답 도출 |
| 6 | 적용된 Flyway 마이그레이션 파일을 왜 고치면 안 되는가 | "Dirty Checking시 탈락한다" → (용어 정정 후) "체크섬이 달라지고 Flyway는 오류가 난다" | ⚠️→✅ | "Dirty Checking"은 오늘 배운 Hibernate 변경 감지(D5)와 용어 혼동. 정정 후 체크섬 불일치→기동 거부로 정확히 답함 |
| 7 | 영속성 컨텍스트가 `save()` 없이 `UPDATE`를 만드는 원리(오늘 실험 근거) | "managed 상태 필드만 바꾸고 flush 시점에 자동 UPDATE" | ✅ | Day12 실험과 정확히 일치 |
| 8 | `@RestControllerAdvice`로 Controller마다 try-catch가 불필요한 이유 | (힌트 후) "어차피 Spring Exception handler로 전부 통하니까 알아서 처리해준다" | ✅ | 전역 등록된 단일 Bean이 모든 Controller의 미처리 예외를 라우팅받는다는 핵심은 도달, 표현은 다소 느슨함 |

## 총평

8/8 최종 통과. 다만 3·5·6·8번은 힌트 없이는 답하지 못했고, 2번은 인과관계가 반대로 정리돼 있었다. 13일 만의 재개(8/9→8/22)로 Week A 후반부(DI·싱글톤 이유)와 Flyway 용어가 가장 많이 흐려져 있었다 — 두 영역 모두 복습큐에 재등록한다.
