# Day12 (8/22, Week B D5) 용어

주제: 변경 감지(Dirty Checking) · flush 시점

## 1. 변경 감지

| 용어 | 한줄뜻 | 오늘 코드/관찰 |
|---|---|---|
| 변경 감지(Dirty Checking) | 영속성 컨텍스트가 관리 중인 Entity의 현재 값을, 그 Entity를 로드(또는 저장)한 시점의 스냅샷과 비교해 다르면 자동으로 `UPDATE`를 만드는 동작 | `managed.cancel()`만 호출하고 `save()`는 호출하지 않았는데 `UPDATE`가 나감 |
| 스냅샷 | Entity가 영속성 컨텍스트에 들어온(로드되거나 저장된) 시점의 필드 값 사본. 변경 감지는 현재 값과 이 스냅샷을 비교한다 | 저장 시점에 `confirmed=true`였다가 나중에 `cancel()`로 `false`가 되면 스냅샷(`true`)과 현재값(`false`)이 달라 dirty로 판정됨 |
| `flush()` | 영속성 컨텍스트의 변경 사항(dirty로 판정된 Entity 포함)을 실제 SQL로 DB에 내보내는 시점 | `entityManager.flush()` 호출 시 대기 중이던 `UPDATE`가 실행됨 |
| `save()`의 실제 역할 | 새 객체를 영속화하거나 갱신을 강제로 트리거하는 **편의 메서드**일 뿐, "저장"의 유일한 경로가 아니다 | 이미 관리 중인 Entity는 `save()` 없이 필드만 바꿔도 flush 시점에 반영됨 |

## 2. 실험으로 확인한 것

1. `confirmed=true`로 예약을 저장해 DB에 반영해둔다.
2. 같은 트랜잭션 안에서 그 예약을 다시 조회한다 → 영속성 컨텍스트가 이 객체를 관리 중으로 붙잡는다(로드 시점 스냅샷: `true`).
3. `managed.cancel()`로 필드만 바꾼다. **`repository.save()`는 절대 호출하지 않는다.**
4. `entityManager.flush()`를 호출하면 Hibernate가 스냅샷(`true`)과 현재 값(`false`)의 차이를 발견하고 알아서 `UPDATE`를 만들어 보낸다.
5. `clear()`로 캐시를 비우고 다시 조회해 DB에 실제로 반영됐는지(`confirmed == false`) 확인한다.

즉 JPA에서 "저장"은 `save()` 호출이 아니라 **관리 중인 객체의 필드를 바꾸는 행위 자체**다.

## 3. 이번 실험을 짜면서 겪은 시행착오 (구성 판단)

같은 트랜잭션 안에서 `confirm()` 뒤에 바로 `cancel()`을 호출하면, 로드된 스냅샷과 최종 값이 같아져(둘 다 `false`) 아무것도 증명하지 못하는 테스트가 된다. **의미 있는 변경 감지 실험이 되려면, 상태를 바꾸는 호출이 "로드 시점 스냅샷과 다른 최종값"을 만들어야 한다** — 그래서 `confirm()`은 최초 저장 이전(생성자 직후)으로 옮기고, 트랜잭션 안에서는 `cancel()` 한 번만 남겼다.
