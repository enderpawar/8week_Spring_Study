# Day별 전체 흐름(Big Picture) 그림 추가 명세 (2026-09-23)

## 1. 목적

각 Day 글에 **그날 주제의 전체 흐름을 한 장으로 보여 주는 그림**을 1장 넣는다.

- 입문자가 봐도 "요청이 어디서 들어와 어디를 거쳐 어디로 나가는지"가 바로 잡혀야 한다.
- 백엔드 개발자를 뽑는 인사담당자가 보고 "이 사람은 구조를 제대로 이해했다"고 느낄 만큼 깔끔하고 짜임새 있어야 한다.

공식 문서가 아니어도 된다. 대신 **출처를 정확히 남긴다.**

기존 자체 UML은 "우리 코드의 세부 흐름"을 맡고, 이번 그림은 "업계 표준 구조 속 전체 위치"를 맡는다.

## 2. 출처

- **허용:** 기술 블로그, Baeldung·GeeksforGeeks 같은 튜토리얼 사이트, 기업 기술 블로그, Medium·velog·tistory, Stack Overflow, 공식 문서, Wikimedia 등 공개 웹페이지
- **금지:**
  - 원 게시 페이지를 확인할 수 없는 이미지(검색 썸네일, 이미지 모음 사이트, 핀터레스트 재게시)
  - 워터마크나 광고가 그림을 크게 가리는 이미지
  - AI 생성으로 보이는 부정확한 도식
- **출처 줄 형식:** `*출처: [게시물 제목](원 게시 페이지 URL) — 작성자 또는 사이트명. 저작권은 원저작자에게 있습니다.*`
  - 라이선스가 명시돼 있으면(CC BY-SA 등) 끝에 덧붙인다.

## 3. 채택 조건 (전부 만족)

1. **정확성:** 우리 스택(Spring Boot 3.5, Jakarta, 내장 Tomcat 10.1, Spring Data JPA/Hibernate 6, H2, Flyway)과 본문 설명에 어긋나지 않는다.
   - 옛 이름(`javax`, `SCHEMA_VERSION` 등)이나 잘못된 순서가 있으면 거부한다.
   - View·ViewResolver 경로가 들어간 MVC 그림은 소개 문장에 "`@RestController`는 View 단계를 건너뛰고 HttpMessageConverter로 본문을 쓴다"는 한 줄을 붙일 때만 허용한다.
2. **전체 흐름:** 부분 확대도가 아니라 그날 주제의 시작부터 끝까지가 한 장에 담긴 그림이어야 한다.
   - 예: 클라이언트 → Tomcat → Filter → DispatcherServlet → HandlerMapping → Controller → MessageConverter → 응답
3. **입문자 가독성:** 약 760px 폭에서 모든 라벨이 읽히고, 한눈에 구조가 들어와야 한다. 생명선 수십 개짜리 도식은 거부한다.
4. **시각 품질:** 정돈된 레이아웃과 일관된 색·서체를 갖춰야 한다. 흐리거나 저해상도이거나, 손그림 스캔이면 거부한다.
5. **검수:** `curl`로 다운로드해 `200 image/*`를 확인하고, **Read로 직접 열어** 위 조건을 판단한다. 판단 내용은 보고서에 한 줄로 쓴다.

- **기존 그림과의 관계**
  - 기존 자체 UML(`dayNN-*.png`)은 절대 삭제하지 않는다.
  - 기존 공식 그림(`dayNN-web-*`)이 새 전체 흐름 그림과 역할이 완전히 겹치면 삭제해도 된다. 이때 본문의 이미지 블록 전체(소개 문장, 이미지, 주석, 출처)와 assets 파일을 함께 지우고 보고한다.

## 5. 규칙

- 소개 문장 한 줄과 이미지 블록 외에는 본문을 수정하지 않는다. 목차를 추가하거나 번호를 바꾸지 않는다.
- 외부 요청에 이메일 등 개인정보를 User-Agent·헤더·URL로 보내지 않는다. 기본 UA나 `Mozilla/5.0`만 쓴다.
- 담당 파일 외에는 수정하지 않는다. 커밋하지 않는다.
- 조건을 만족하는 그림을 끝내 못 찾으면 0장도 허용한다. 대신 검토한 후보와 거부 사유를 구체적으로 보고한다.
