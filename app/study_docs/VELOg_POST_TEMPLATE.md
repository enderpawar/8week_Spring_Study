# Spring 기본기 기술 블로그 템플릿

> 목적: 한 글을 두 독자에게 유용하게 만든다. 채용 담당자·기술 면접관은 첫 부분만 읽어도 문제 해결 과정과 검증 수준을 파악하고, 학습자는 전체 글을 다시 읽으며 이론과 오답을 인출한다.

## 1. 이 템플릿의 독자와 작성 목표

### 빠르게 훑는 독자

- 대상: 채용 담당자, 기술 면접관, 동료 개발자
- 첫 1분 안에 확인할 내용: 무엇을 배웠는지, 왜 필요했는지, 어떤 판단을 했는지, 무엇으로 검증했는지, 아직 어떤 한계가 있는지

### 다시 공부하는 독자

- 대상: 미래의 나, 같은 개념을 처음 배우는 주니어 개발자
- 글 전체에서 확인할 내용: 정확한 용어, 동작 흐름, CS 연결, 실제 코드, 예측과 결과의 차이, 오답 교정, 인출 질문

좋은 인상을 직접 주장하지 않는다. 코드·테스트·실패 원인·설계의 한계처럼 독자가 확인할 수 있는 증거로 보여준다.

## 2. 반드시 지킬 작성 원칙

1. **한 글에는 중심 주제를 하나만 둔다.** 곁가지 문법 오류는 중심 개념의 이해에 영향을 준 경우에만 남긴다.
2. **서두에는 검증된 사실만 요약한다.** 실행하지 않은 테스트, 완성하지 않은 기능, 측정하지 않은 수치를 성공처럼 쓰지 않는다.
3. **이론을 구현보다 먼저 설명한다.** 필요성 → 용어 → 동작 흐름 → CS 연결 → 현재 코드 순으로 쓴다.
4. **코드보다 판단을 설명한다.** 왜 이 구조를 선택했고 어떤 대안과 trade-off가 있었는지 밝힌다.
5. **실수는 선별해 기록한다.** 단순 오타를 나열하기보다 잘못된 멘탈모델, 발견 방법, 재발 방지 수단을 설명한다.
6. **한계를 숨기지 않는다.** 미처리 예외, 테스트 공백, 임시 구현을 기술 부채와 다음 실험으로 명시한다.
7. **학습자의 목소리를 보존한다.** 실제 답변·의문·발견만 1인칭으로 쓰고 감정·동기·학습 시간은 만들지 않는다.
8. `[직접 작성]`은 절대 덮어쓰지 않는다.
9. 이모지, 과장된 수식어, 홍보성 문장, 목차, 불필요한 태그 나열은 사용하지 않는다.
10. 코드·용어·실행 결과를 최종 검수하고, 깨진 코드를 정상 코드처럼 싣지 않는다.

## 3. 제목 규칙

다음 형식을 기본으로 한다.

```text
[백엔드 기본기 Day N] 핵심 기술 — 해결한 문제 또는 확인한 메커니즘
```

좋은 예:

```text
[백엔드 기본기 Day 4] Service와 Repository — 책임 분리와 식별자의 필요성
[백엔드 기본기 Day 5] IoC와 생성자 주입 — 객체 연결의 제어권은 어디에 있는가
```

피할 예:

```text
오타 소동
드디어 성공
Spring 완전 정복
```

제목에는 실제 글의 중심 개념과 기술적 질문을 넣는다. 실수나 감정을 제목의 중심으로 삼지 않는다.

# [백엔드 기본기 Day N] 핵심 기술 — 해결한 문제 또는 확인한 메커니즘

오늘 학습이 이전 Day의 어떤 코드에서 이어졌는지 2~3문장으로 설명한다. 이 글에서 다룰 범위와 다루지 않을 범위를 분명히 한다. 실제 기록에 없는 감상은 덧붙이지 않는다.

## 한눈에 보기

> 이 영역은 첫 화면에서 읽히는 요약이다. 각 항목을 한두 문장으로 작성한다.

- **문제:** 기존 코드나 멘탈모델에 어떤 문제가 있었는가?
- **적용:** 어떤 개념과 설계를 적용했는가?
- **검증:** 어떤 테스트·빌드·HTTP 요청으로 무엇을 확인했는가?
- **한계:** 아직 해결하지 않았거나 다음 학습으로 넘긴 것은 무엇인가?

## 1. 문제를 이해하기 위한 이론

이 절만 다시 읽어도 오늘 개념을 복습할 수 있어야 한다. 모든 하위 항목을 억지로 길게 쓰지 말고, 중심 주제를 이해하는 데 필요한 내용만 남긴다.

### 왜 필요한가

기술 이름부터 설명하지 말고, 이 개념이 없을 때 현재 코드에 생기는 문제에서 시작한다.

### 핵심 용어

처음 등장한 용어와 약어를 정확히 풀어 쓴다. 비슷한 개념은 차이를 함께 설명한다.

- **용어:** 한국어 설명
- **헷갈리기 쉬운 개념과의 차이:** 공통점 / 결정적 차이

### 동작 흐름

프레임워크 내부 또는 요청 처리 순서를 실제 클래스·메서드 이름으로 나타낸다.

```text
시작점 → Spring의 처리 → 현재 코드 → 관찰 가능한 결과
```

화살표만 두지 말고 각 단계에서 누가 무엇을 하는지 문장으로 설명한다.

### CS 지식과 연결

이미 배운 CS 개념과 공통점·차이를 함께 쓴다. 예: 트랜잭션↔ACID, 인덱스↔B-tree, DI↔의존 그래프 구성. 정확하지 않은 생활 비유는 사용하지 않는다.

### 현재 코드에서 찾기

핵심 개념이 드러나는 파일과 메서드를 구체적으로 연결한다.

- [`파일명`](정확한 GitHub 파일 또는 커밋 링크): 어떤 역할을 하는가
- `Class.method()`: 이론의 어느 부분이 드러나는가

## 2. 설계 선택과 대안

### 선택한 방식

어떤 구조를 선택했는지와 그 이유를 설명한다.

### 고려한 대안과 trade-off

실제로 학습하거나 검토한 대안만 쓴다. 존재하지 않았던 고민을 꾸며내지 않는다.

| 선택지 | 장점 | 단점·적합하지 않았던 이유 |
|---|---|---|
| 현재 선택 |  |  |
| 비교 대상 |  |  |

비교할 대안이 없었던 날에는 이 표와 하위 절을 생략한다.

## 3. 코드로 적용하기

전체 파일을 복사하지 않고 설계 판단을 보여주는 최소 코드만 싣는다. 코드가 길면 저장소 링크로 대신한다.

```java
// 실제 빌드 또는 테스트로 확인한 핵심 코드
```

코드를 실행 순서대로 설명하고, 각 애노테이션·메서드가 왜 필요한지 현재 예제 안에서 풀어 쓴다. 최종 코드와 글의 클래스·메서드 이름이 일치하는지 확인한다.

## 4. 예측 → 실행 → 차이 설명

실행 전에 실제로 답한 예측을 보존한다. 정답으로 미리 고쳐 쓰지 않는다.

| 구분 | 기록 |
|---|---|
| 실행 전 예측 | `[직접 작성]` 실제 답변 |
| 실행 또는 테스트 | 실제로 수행한 방법 |
| 실제 결과 | 확인된 출력·상태 코드·예외·쿼리 |
| 차이의 원인 | 어떤 멘탈모델이 맞거나 틀렸는지 |

예측이 맞았어도 원리를 다시 설명한다. 실행하지 못했다면 `미검증`이라고 명시하고 결과를 추측하지 않는다.

## 5. 검증 근거

독자가 재현할 수 있을 정도로 적되, 학습 목적이 아닌 셸 명령 암기 글로 만들지 않는다.

| 검증 대상 | 검증 방법 | 확인한 결과 |
|---|---|---|
| 컴파일 또는 컨텍스트 | 예: `./gradlew test` | 실제 성공·실패 결과 |
| 정상 경로 | 테스트명 또는 HTTP 요청 | 실제 응답 |
| 실패·경계 경로 | 테스트명 또는 HTTP 요청 | 실제 응답·예외 |

검증하지 않은 행은 채우지 말고 삭제한다. 가능한 경우 해당 Day 커밋, 테스트 파일, 핵심 소스에 직접 연결한다. 저장소 첫 화면만 반복해서 연결하지 않는다.

## 6. 막힌 지점과 오답 교정

모든 오타를 나열하지 않는다. 중심 개념이나 디버깅 능력을 보여주는 사례를 다음 구조로 정리한다.

### 증상

실제 오류 메시지나 예상과 달랐던 동작을 짧게 제시한다.

### 처음 생각

사용자가 실제로 했던 설명만 기록한다.

### 원인

문법·타입·프레임워크 동작·설계 중 어느 층의 문제였는지 구분한다.

### 교정과 재발 방지

무엇을 고쳤고, 테스트·타입·상수·설계 변경 중 어떤 장치가 같은 문제를 막는지 설명한다.

## 7. 현재 한계와 다음 개선

현재 구현을 완성된 서비스처럼 포장하지 않는다.

- **현재 한계:** 실제 코드로 확인된 미처리 사항 또는 임시 구현
- **영향:** 어떤 입력·규모·환경에서 문제가 되는가
- **다음 단계:** 로드맵상 언제 어떤 실험으로 확인할 것인가

이 절은 약점을 고백하는 공간이 아니라, 현재 시스템의 경계를 이해하고 우선순위를 판단하는 증거다.

# 여기부터는 작성자용 규칙이며 게시 글에 포함하지 않는다

## 게시 전 품질 게이트

### 사실과 기술 정확성

- [ ] 현재 소스와 글의 클래스·메서드·경로가 일치하는가?
- [ ] 코드가 컴파일되거나 테스트된 상태인지 확인했는가?
- [ ] 실행하지 않은 결과와 측정하지 않은 수치를 만들지 않았는가?
- [ ] Spring·Java·HTTP 용어를 정확히 사용했는가?
- [ ] 실제 오답과 최종 교정 내용을 구분했는가?

### 복습 가치

- [ ] 이론이 필요성 → 용어 → 흐름 → CS 연결 → 실제 코드 순서로 설명됐는가?
- [ ] 인출 질문을 답을 보기 전에 풀 수 있는 구조인가?
- [ ] 예측과 실제 결과의 차이가 멘탈모델 수준에서 설명됐는가?
- [ ] 이 글 하나만 읽어도 중심 개념을 다시 설명할 수 있는가?

### 포트폴리오 가치

- [ ] 첫 화면에서 문제·적용·검증·한계가 보이는가?
- [ ] 코드 나열보다 설계 선택과 근거가 중심인가?
- [ ] 의미 있는 실패만 원인과 재발 방지까지 설명했는가?
- [ ] 구체적인 소스·테스트·커밋 링크가 있는가?
- [ ] 현재 한계와 다음 개선이 정직하게 구분됐는가?
- [ ] 과장, 자책, 지나치게 가벼운 표현 없이 차분한 학습자 목소리인가?

### 편집 품질

- [ ] 제목만 읽어도 핵심 기술과 질문을 알 수 있는가?
- [ ] 같은 설명을 이론·코드·Q&A에서 반복하지 않았는가?
- [ ] 긴 문장을 나누고 모호한 `이것`, `저것`의 대상을 밝혔는가?
- [ ] 코드 블록에 언어를 지정하고 표·목록의 형식을 통일했는가?
- [ ] `[직접 작성]` 내용을 보존했는가?
- [ ] 비밀값·토큰·개인정보가 포함되지 않았는가?

## 분량 조절 규칙

- 모든 절을 억지로 채우지 않는다. 해당 Day에 근거가 없는 선택·테스트·회고는 생략한다.
- 한 코드 블록은 한 가지 판단만 보여준다. 전체 구현은 소스 링크로 연결한다.
- 단순 오타는 한 문장으로 묶고, 중심 원리를 드러내는 오류만 자세히 다룬다.
- 매일의 원본 퀴즈·단어장·설명 로그는 저장소에 유지하고, Velog 글에는 중심 서사에 필요한 내용만 선별한다.
- 글이 너무 길어지면 이론을 삭제하지 말고 부수적인 오류 로그와 반복 코드를 줄인다.
