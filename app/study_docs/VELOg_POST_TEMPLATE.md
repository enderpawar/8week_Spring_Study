# Spring 기본기 기술 블로그 템플릿

> 목적: **검증된 학습 기록에서 선별한 공개 글**을 쓴다. 채용 담당자·기술 면접관·같은 개념을 공부하는 개발자가 읽고, 무엇을 판단했고 무엇으로 검증했는지 확인할 수 있어야 한다.

## 1. 이 템플릿의 독자와 작성 목표

### Day별로 쓰되, D6·D7 마무리 주간은 한 편으로 합친다

기본적으로 Day별로 계속 쓴다. 날짜순으로 쌓인 연속 기록 자체가 성실성의 증거이고, 이건 몇 편 몰아 쓰는 방식으로는 만들 수 없다.

단, **각 주의 D6 누적시험과 D7 버퍼는 공개 Velog 글 한 편으로 합친다.** 두 날은 새 개념을 각각 강의하는 날이 아니라, 한 주의 인출 결과를 확인하고 오답·기술부채를 코드에 반영하는 연속 과정이기 때문이다. 서로 다른 날에 진행하더라도 D6에 초안을 열고 D7 완료 후 한 편으로 확정한다. `vocab.md`·`quiz.md`·`explain-log.md`·`progress.md`는 Day별 증거로 계속 분리하고, 게시용 글만 `study_docs/velog/`에 통합한다.

대신 **모든 날에 같은 분량을 요구하지 않는다.** 소재가 얕은 날 분량을 맞추려고 절을 채우면 그건 성실성이 아니라 판단력 부족으로 읽힌다. 독자는 전체를 읽지 않고 한두 편만 클릭하므로, **가장 약한 글 한 편이 시리즈 전체의 인상을 결정한다.**

- Light 소재: 60~90줄
- Full 소재: 120~165줄
- 근거가 없는 절은 채우지 말고 생략한다

이 숫자는 Day01~05를 커버리지 대조로 쓴 실측치다(126~165줄). 처음에는 90~110줄로 잡았다가, 그날 배운 걸 다 담으면 지킬 수 없는 기준이라는 게 드러나 고쳤다. **분량을 맞추려고 개념을 빼지 않는다.** 줄여야 하면 반복된 설명과 곁가지 오류 로그를 먼저 자른다.

**주 1편은 그 주에서 가장 좋은 주제를 골라 심화글로 승격**한다. 여러 Day를 하나의 기술적 질문으로 묶고 `Day N` 접두사 없이 쓴다. 이 글이 채용 독자용 대표작 역할을 한다.

D6·D7 통합 마무리 글은 이 주간 대표작을 겸할 수 있다. 시험과 코드 적용 사이에 하나의 서사가 있으면 별도의 심화글을 억지로 추가하지 않는다.

Day 완료는 `vocab.md`·`quiz.md`·`explain-log.md`로 판정한다. **글이 밀렸다는 이유로 다음 Day 진도를 막지 않는다.**

### 이 글은 인출 복습 도구가 아니다

인출은 글을 **읽기 전에** `quiz.md`와 `복습큐.md`에서 한다. 노트를 덮고 먼저 답하고 대조하는 것이 인출이고, 완성된 글을 다시 읽는 것은 인출이 아니다. 복습은 이 글을 **쓰는 과정**에서 일어난다.

따라서 일반 Day 글에는 정답이 달린 Q&A 절을 만들지 않는다. 필요하면 정답 없는 면접 질문을 1~2개만 남긴다.

**D6·D7 마무리 글은 예외다.** 이미 끝난 시험의 실제 오답을 “최초 답변 → 왜 틀렸나 → 교정된 기준 → 코드 적용” 순서로 공개할 수 있다. 다만 새로운 문제와 모범답안을 추가해 인출 문제집처럼 만들지는 않는다.

### 두 층의 독자

- **첫 화면만 읽는 독자** — 채용 담당자, 빠르게 훑는 면접관. `한눈에 보기`에서 문제·적용·검증·한계를 파악한다.
- **본문까지 읽는 독자** — 기술 면접관, 같은 개념을 공부하는 개발자. 메커니즘·설계 판단·검증 근거를 확인한다.

좋은 인상을 직접 주장하지 않는다. 코드·테스트·실패 원인·설계의 한계처럼 독자가 확인할 수 있는 증거로 보여준다.

## 2. 반드시 지킬 작성 원칙

1. **한 글에는 중심 질문을 하나만 둔다.** 곁가지 문법 오류는 중심 개념의 이해에 영향을 준 경우에만 남긴다.
2. **서두에는 검증된 사실만 요약한다.** 실행하지 않은 테스트, 완성하지 않은 기능, 측정하지 않은 수치를 성공처럼 쓰지 않는다.
3. **코드보다 판단을 설명한다.** 왜 이 구조를 선택했고 어떤 대안과 trade-off가 있었는지 밝힌다. 실제로 비교한 대안이 없었으면 현재 선택의 이유만 쓰고, 없던 고민을 꾸며내지 않는다.
4. **메커니즘은 삭제하지 않고 압축한다.** 정확한 용어와 동작 흐름은 이 글의 핵심 가치다. 분량을 줄일 때는 반복된 설명과 부수적 오류 로그를 먼저 줄인다.
5. **실수는 선별해 기록한다.** 단순 오타를 나열하기보다 잘못된 멘탈모델, 발견 방법, 재발 방지 수단을 설명한다. 예측의 차이와 오답 교정은 **하나의 서사로 합쳐 쓴다.**
6. **한계를 숨기지 않되 반복하지 않는다.** 그 글의 주제와 직접 관련된 1~2개만 쓰고, 바로 고칠 것·나중에 고칠 것·고치지 않을 것 중 하나로 분류한다. 전체 목록은 `기술부채.md`에서 관리하며 매 글에 복사하지 않는다.
7. **기술 주장을 과하게 일반화하지 않는다.** "~하려면 X 없이는 방법이 없다"류의 문장은 반례를 확인한 뒤에만 쓴다. 관찰한 사실과 가능한 대안을 구분한다.
8. **학습자의 목소리를 보존한다.** 실제 답변·의문·발견만 1인칭으로 쓰고 감정·동기·학습 시간은 만들지 않는다.
9. `[직접 작성]`은 절대 덮어쓰지 않는다.
10. 이모지, 과장된 수식어, 홍보성 문장, 목차, 불필요한 태그 나열은 사용하지 않는다.
11. 코드·용어·실행 결과를 최종 검수하고, 깨진 코드를 정상 코드처럼 싣지 않는다.

## 3. 제목 규칙

시리즈 글은 다음 형식을 기본으로 한다.

```text
[백엔드 기본기 Day N] 핵심 기술 — 해결한 문제 또는 확인한 메커니즘
```

여러 Day를 묶은 심화글은 `Day N` 접두사 없이 **기술 주제를 제목 앞에** 둔다. Day 정보는 부제나 시리즈 표기로 내린다.

```text
빌드 성공은 왜 API 계약 검증이 아닌가 — @PathVariable 누락을 테스트로 잡기
```

각 주의 D6·D7을 합친 마무리 시험 글은 다음 제목을 사용한다.

```text
[백엔드 기본기 DAY 6 & DAY 7] 1주차 마무리 시험
[백엔드 기본기 DAY 13 & DAY 14] 2주차 마무리 시험
```

Day 번호와 주차만 바꾸고, 억지로 개념 키워드를 제목에 추가하지 않는다. 이 글의 중심은 새 개념 하나가 아니라 한 주의 인출·교정·적용 기록이다.

피할 예:

```text
오타 소동
드디어 성공
Spring 완전 정복
```

제목에는 실제 글의 중심 개념과 기술적 질문을 넣는다. 실수나 감정을 제목의 중심으로 삼지 않는다.

### D6·D7 주차 마무리 시험 글의 구조

D6·D7 통합 글은 아래의 일반 H2 네 개를 강제로 따르지 않는다. 그 주의 실제 기록에 맞춰 다음 순서를 기본 골격으로 사용한다.

1. **시험 범위와 진행 방식** — 그 주의 Day 범위, 이번에 실제로 도래한 인출 항목, 함께 진행한 이유
2. **시험에서 틀린 문제** — 실제 오답만 골라 최초 답변과 교정된 판단 기준 기록
3. **D7 코드 적용** — 시험에서 교정한 개념이 기술부채·독립과제에 어떻게 연결됐는지 설명
4. **자동 검증 범위** — 단위·통합·HTTP 테스트와 미검증 범위를 구분
5. **주차 마무리와 다음 시작점** — 이해가 어떻게 바뀌었는지, 다음 주 첫 Day가 무엇인지 명시

유연하게 줄이거나 합쳐도 되지만, 다음 규칙은 지킨다.

- 새로운 개념 강의처럼 용어를 길게 나열하지 않는다.
- 실제 시험 결과가 없는 문항을 통과·오답으로 만들지 않는다.
- D6 인출과 D7 구현이 어떤 판단으로 연결됐는지 한 번은 보여준다.
- 시험 결과표는 실제 확인 항목만 싣고, 기존 `quiz.md` 전체를 복사하지 않는다.
- 코드 블록은 오답이 실제 구현으로 바뀐 핵심 지점만 선택한다.
- 마지막에 다음 주의 첫 미완료 Day를 적는다.
- 분량은 고정하지 않는다. 반복을 제거한 뒤 120~180줄을 넘으면 공개 가치가 낮은 세부 로그가 섞였는지 점검한다.

# 제목

> **아래 일반 템플릿은 개념·구현 Day에 사용한다. D6·D7 통합 마무리 글에는 위 전용 구조를 사용한다.** 일반 글의 H2 네 개는 고정이지만 각 절 안의 H3 소제목은 그날 내용으로 새로 짓는다.

이 글이 다루는 기술적 질문이 어떤 코드에서 나왔는지 2~3문장으로 설명한다. 다룰 범위와 다루지 않을 범위를 분명히 한다. 이전 글을 언급할 때는 그 글의 실제 클래스·경로와 일치하는지 확인한다.

> 첫 화면 요약. 오늘 뭘 했고, 뭘 알아냈고, 어디까지 검증했는지를 2~3문장으로 쓴다. 라벨을 붙이지 말고 산문으로 쓴다.

## 1. 개념 설명

**이 절만 다시 읽어도 그날 개념을 복원할 수 있어야 한다.** 다른 절에 설명이 있더라도 개념 자체가 여기 정리 안 됐으면 결함이다.

`vocab.md`의 용어를 표로 먼저 싣는다. 열은 **3개까지**만 — 4열 이상은 velog·모바일에서 셀이 깨진다. `연관 단어` 열은 표에서 빼되 버리지 말고 절 끝의 "더 볼 것"으로 옮긴다.

| 용어 | 한줄뜻 | 코드 모습 |
|---|---|---|
|  |  |  |

표 아래 산문은 **정의를 반복하지 않는다.** 표가 정의를 담았으니 산문은 *그 용어들이 서로 어떻게 이어지는지*를 쓴다.

관계가 설명의 핵심인 날에는 흐름 그림을 넣는다. 문단 벽보다 읽기 쉬우므로 가독성에도 이득이다.

```markdown
![흐름 설명 대체텍스트](../../assets/dayNN-....svg)
```

문단은 2~3줄로 끊는다. 핵심 주장은 인용 블록이나 목록으로 뽑아 시선 앵커를 만든다. 4~6줄짜리 문단을 연속으로 두지 않는다.

> **더 볼 것**
> - [공식 문서 제목](URL): 이 글의 어느 주장에 대한 근거인지
> - 아직 안 본 것 — `vocab.md`의 연관 단어 중 오늘 범위 밖이었던 것

## 2. 코드 구현

H3 소제목을 그날 내용으로 짓는다. 예: `` ### `/health` — 상태코드를 직접 명시하기 ``, `### bootRun은 코드 수정할 때마다 다시 돌려야 한다`, `### 예측이 틀렸던 지점 — 취소했는데 예약이 하나 더 생김`.

각 소절은 **코드 → 무슨 일이 일어났나 → 왜** 순으로 쓴다. 전체 파일을 붙이지 말고 판단이 드러나는 최소 코드만 싣는다.

마지막 소절은 검증으로 닫는다.

### 오늘 확인한 것

실제 요청과 응답, 빌드·테스트 결과를 적는다. **자동 테스트·수동 확인·미검증을 반드시 구분**하고, 실행하지 않은 결과는 추측하지 않는다. 해당 Day 커밋 permalink를 남긴다.

## 3. 스스로 답한 질문

그날 실제로 막혔던 질문을 H3로 세우고 답한다. `quiz.md`·`explain-log.md`·커밋 주석에 남은 진짜 의문만 쓰고, 없던 질문을 지어내지 않는다.

각 답은 **처음 답 → 왜 틀렸나 → 교정된 답 → 재발 방지** 순서로 쓴다. 학습자의 실제 오답 표현을 원문 그대로 보존한다.

예측과 오답 교정은 여기 하나로 합친다. 별도의 예측 표를 만들지 않는다 — 자문자답이 원래 그 형식이다.

## 4. 정리하며

새로 외운 용어가 아니라 **이해가 어떻게 바뀌었는지**를 1~2문단으로 요약한다.

마지막 문단에 **아직 남은 것**을 쓴다. 그 글의 주제와 직접 관련된 한계 1~2개만 골라, 무엇이 문제이고 어떤 상황에서 터지는지와 함께 **바로 고칠 것 / 나중에 고칠 것(해결 Day) / 고치지 않을 것** 중 하나로 분류한다. 전체 목록은 `기술부채.md`에 있으므로 옮겨 적지 않는다.

남길 게 있으면 정답 없는 면접 질문을 1~2개 덧붙인다. 정답과 재시험 도래일은 `quiz.md`와 `복습큐.md`가 관리한다.

# 여기부터는 작성자용 규칙이며 게시 글에 포함하지 않는다

## 구조 예산 (분량보다 우선)

일반 글의 절 개수는 **표준 5개, 최소 4개**다. 근거가 없는 절은 꾸며내지 말고 생략한다. D6·D7 통합 글은 전용 구조를 따르되 실제 시험·구현 기록에 따라 절을 합칠 수 있다.

- 같은 핵심 주장은 `한눈에 보기`와 상세 본문, **최대 두 번**만 등장한다
- H2는 4~5개
- 중심 실험은 1개. 복잡한 Full Day만 2개
- 코드 블록 1~2개, 합계 핵심 코드 30줄 이내
- 검증 표는 최대 3행
- 공개할 한계는 중요도순 1~2개
- 한 문단이 새 메커니즘·판단·증거·영향 중 아무것도 추가하지 않으면 삭제한다

글자 수는 실패 조건이 아니라 경고선이다(비코드 본문 기준).

## 시각 자료

다이어그램은 요청 흐름·계층·의존 관계·프록시처럼 **관계가 설명의 핵심일 때만** 넣는다. 모든 글에 넣지 않는다.

### 표기법은 UML을 쓴다

박스와 화살표를 임의로 그리면 맞고 틀리고가 없어서 아무 신호도 되지 못한다. **UML은 정확성을 남이 검증할 수 있다** — 이 시리즈가 커밋 permalink와 미검증 표기로 쌓는 신뢰와 같은 축이다.

다만 **표기법이 틀리면 안 쓰느니만 못하다.** "모양만 배웠구나"로 읽힌다. 내용에 맞는 종류를 고르는 것이 첫 단계다.

| 설명하려는 것 | 쓸 다이어그램 |
|---|---|
| 시간 순서로 일어나는 호출·반환, 조건 분기 | **시퀀스** (`alt`/`opt` 프레임) |
| 타입의 구조, 가시성, 상속·구현·의존 관계 | **클래스** |
| 실행 중 한 시점의 인스턴스와 링크 | **객체** |
| 상태 전이 | **상태 머신** |

**유스케이스 다이어그램은 거의 쓸 일이 없다.** 액터가 시스템에 무엇을 원하는지를 그리는 표기법이라, 프레임워크 내부 동작이나 클래스 구조에는 맞지 않는다. Day01을 유스케이스로 그리면 `사용자 → 인사말 조회` 하나로 끝나고 `DispatcherServlet`이 낄 자리가 없다.

지켜야 할 표기:

- **시퀀스** — 실선+채운 화살촉은 호출, 점선+열린 화살촉은 반환. 생명선은 점선, 제어권을 쥔 구간은 활성화 막대. 분기는 `alt` 프레임에 오각형 라벨
- **클래스** — 이름/속성/오퍼레이션 3칸. `+` public, `-` private. `«interface»`·`«record»` 같은 스테레오타입. `final`은 `{readOnly}` 제약. 실현은 점선+속 빈 삼각 화살촉, 의존은 점선+열린 화살촉
- **객체** — 인스턴스명에 밑줄(`r1 : Reservation`), 링크는 화살촉 없는 실선
- **노트** — 오른쪽 위 모서리를 접은 사각형에 점선으로 연결

**그림에 문장을 넣지 않는다.** 설명은 본문이 한다. 도표 안에 설명 문단이 들어가기 시작하면 그건 다이어그램이 아니라 인포그래픽이고, 만든 티가 난다. 노트는 그림만으로 오해할 수 있는 한 가지를 짚을 때만 쓴다.

색은 기본 한 톤(`#334155`)으로 하고, **오류·주의 경로에만** 두 번째 색을 쓴다. 채움은 흰색.

### 외부 이미지를 가져올 때

1. URL이 실제로 200을 반환하는지 확인한다
2. **이미지를 직접 열어서 내용이 맞는지 확인한다.** 이 단계를 건너뛰지 않는다
3. 라이선스와 안정성을 확인한다 — 공식 문서 / Wikimedia CC / 저장소 자산 순으로 우선
4. 통과하면 `![설명](url)`로 본문에 넣고 아래에 출처를 한 줄 남긴다

남의 블로그 이미지는 핫링크하지 않는다. 링크가 깨지고, 포트폴리오 글에 출처 없는 남의 그림이 박히는 건 실제 리스크다.

**2단계가 실제로 사고를 막은 사례.** `docs.spring.io`의 유일한 MVC 흐름 다이어그램(4.3.x 레거시)은 살아 있지만, 열어보니 `model → View template → Render response` 경로였다. `@RestController`는 뷰 해석을 건너뛰므로 그 글에 넣었으면 정반대 멘탈모델을 심었을 것이다. 참고로 현행 Spring 문서에는 이 다이어그램 자체가 없다.

### 직접 만들 때 — SVG로 만들고 PNG로 내보낸다

정확도와 저작권이 둘 다 해결되므로 이쪽이 기본이다. **원본은 SVG, 게시용은 PNG**로 둘 다 만든다.

- **SVG가 원본이다.** 텍스트라 diff가 남고 수정이 쉽다. `study_docs/assets/dayNN-주제.svg`
- **PNG가 게시본이다.** velog 에디터는 이미지 파일을 드래그하면 자체 CDN에 올리고 URL을 꽂아주는데, PNG는 어디서든 확실히 받아준다. `study_docs/assets/dayNN-주제.png`
- 흰 배경(`<rect fill="#ffffff">`)을 반드시 명시한다. 배경을 비우면 velog 다크 모드에서 검은 글자가 사라진다
- 폰트는 한글이 포함된 스택으로 — `system-ui, 'Segoe UI', 'Malgun Gothic', 'Apple SD Gothic Neo', sans-serif`
- SVG 안에서 백틱(`` ` ``)은 마크다운이 아니라 **글자 그대로 찍힌다.** 코드 강조는 색과 monospace 폰트로 한다
- 폭은 820~860px. 그 이상은 velog 본문에서 축소돼 글자가 뭉갠다

**PNG 내보내기와 검수는 같은 작업이다.**

```bash
# assets 폴더에서 로컬 서버를 띄우고 (file:// 은 Chrome이 막는다)
python -m http.server 8933 --bind 127.0.0.1

# 헤드리스 Chrome으로 렌더 → PNG
chrome.exe --headless=old --disable-gpu --hide-scrollbars \
  "--screenshot=assets/dayNN-주제.png" "--window-size=860,580" \
  "http://127.0.0.1:8933/dayNN-주제.svg"
```

뽑은 PNG를 **반드시 열어서 눈으로 확인한다.** 텍스트가 상자를 넘치는지, 겹치는지, 잘리는지는 좌표만 봐서는 모른다.

### 본문에 거는 법과 velog 게시

MD 본문에는 **PNG를 상대 경로로** 건다. 저장소에서 바로 보이고, velog에 올릴 파일과 같은 것이라 헷갈리지 않는다.

```markdown
![흐름 설명 대체텍스트](../../assets/dayNN-주제.png)
```

velog에 올릴 때:

1. 글 본문을 velog 에디터에 붙여넣는다
2. 이미지 자리에 `assets/dayNN-주제.png`를 **드래그 앤 드롭**한다 — velog가 업로드하고 `![](https://velog.velcdn.com/images/...)` 형태로 바꿔준다
3. 저장소 상대 경로(`../../assets/...`)는 **velog에서 절대 렌더되지 않는다.** 반드시 위 단계로 교체한다

대체텍스트는 파일명이 아니라 **그림이 말하는 내용**을 쓴다. 이미지가 안 뜰 때 그 문장만 읽어도 흐름을 알 수 있어야 한다.
